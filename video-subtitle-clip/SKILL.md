# Video Subtitle Clip

영상 구간 + 자막 → 완성 MP4. 유튜브든 로컬 파일이든 같은 파이프라인을 탄다.

## 이 스킬이 존재하는 이유

이 작업은 단계마다 조용히 실패한다. 확장자가 내용물과 다르고, 자막 인코딩이 CP949고, ffmpeg에 libass가 없고, 구간을 자르면 자막 타임코드가 어긋난다. 매번 처음부터 부딪히면 30분씩 날아가므로, 아래 검증된 경로와 스크립트를 따른다.

## 🪟 윈도우에서 쓸 때 (먼저 읽기)

아래 「환경」 표의 경로는 **맥 기준**이다. 윈도우에서는 이렇게 바꿔 읽는다.

| 도구 | 경로 | 용도 |
|------|------|------|

| `faster_whisper` | pip 패키지 | 윈도우(엔비디아 GPU)·예비 엔진 |

🔴 **받아쓰기는 항상 `scripts/fw_transcribe.py` 로.** 맥·윈도우 공용이고 가장 빠른 엔진을 알아서 고른다 — 엔비디아 GPU면 `cuda`, 맥이면 `cpp`(whisper.cpp), 둘 다 없으면 `cpu`. 출력 JSON 형식이 같아 뒤 단계 스크립트를 그대로 쓴다. `python3 scripts/fw_transcribe.py --check` 로 어느 엔진이 잡히는지 먼저 본다.

**실측 속도 (M3 Pro, 10스레드)** — 예고할 때 이 숫자를 쓴다.

| 방식 | 배속 | 108분 오디오 |
|------|------|-------------|
| `whisper` medium (CPU) | 0.3~1배 | 2~5시간 |
| `fw_transcribe.py` cpu 엔진 (medium int8 + VAD) | 1.5~2.8배 | 40~70분 |
| **`fw_transcribe.py` cpp 엔진 (맥 GPU, large-v3-turbo)** | **약 15~20배** | **약 6분** |
| `fw_transcribe.py` cuda 엔진 (윈도우 RTX) | 아직 실측 없음 — 처음 돌리면 이 칸을 채운다 | |
| 자막 태우기 (1080p, x264 slow crf18) | 약 1배 | 2~3시간 |
| **자막 트랙 심기 (`-c copy`)** | — | **25초** |

🔴 **자막을 태울 땐 반드시 `ffmpeg@7`.** Homebrew가 core `ffmpeg`를 슬림화하며 libass를 빼서, 기본 `ffmpeg`엔 `subtitles`·`ass`·`drawtext` 필터가 아예 없다. 기본 ffmpeg로 시도하면 `Error parsing a filter description` 이 뜨는데, 문법 오류처럼 보여서 따옴표를 고치느라 시간을 버리게 된다. 필터가 없는 것이지 문법이 틀린 게 아니다.

확인:

```bash
/opt/homebrew/opt/ffmpeg@7/bin/ffmpeg -hide_banner -filters | grep -w ass
```

없으면 `brew install ffmpeg@7` (keg-only라 기존 ffmpeg를 건드리지 않는다).

## 워크플로우

### 0. 입력 파악 — 항상 ffprobe 먼저

파일이든 다운로드 후든, 손대기 전에 실제 내용물을 본다. 확장자는 자주 거짓말을 한다 (`.avi`인데 실은 Matroska+Vorbis 같은 경우가 흔하고, 이게 파이널컷이 못 읽는 진짜 원인이다).

```bash
ffprobe -v error -show_entries stream=codec_type,codec_name,width,height,r_frame_rate \
  -show_entries format=duration,format_name -of default=noprint_wrappers=1 "INPUT"
```

`format_name`과 확장자가 다르면 그 사실을 사용자에게 알려준다. 왜 지금까지 안 열렸는지가 거기서 설명된다.

### 1. 소스 확보

**유튜브** — 구간을 이미 알면 그 구간만 받는 게 빠르다:

```bash
yt-dlp -f "bv*[height<=1080]+ba[audio_channels<=2]/b[height<=1080]" \
  --merge-output-format mp4 \
  --download-sections "*19:20-31:50" --force-keyframes-at-cuts \
  -o "%(title).80s.%(ext)s" "URL"
```

`audio_channels<=2` 가 붙어 있는 이유: `ba`(best audio)는 비트레이트만 보고 고르는데, 유튜브가 EAC3 5.1(384k)을 주면 스테레오 후보(114~130k)를 제치고 그게 선택된다. 5.1 은 대사를 센터 채널에만 담아서, 플레이어가 다운믹스를 못 하면 **말소리가 통째로 사라진다**. 파일엔 오디오가 멀쩡히 들어 있어 눈치채기 어렵다.

403 이 나면 순서대로 시도한다 — ① `--cookies-from-browser chrome` ② PO Token 플러그인. 자세한 절차는 `references/troubleshooting.md` 의 「403 Forbidden — PO Token」. 쿠키로 안 풀리는 영상이 실제로 있으므로 쿠키에서 멈추지 않는다.

구간을 모르면 전체를 받는다(`--download-sections` 생략). 다운로드는 되돌리기 쉽지만 용량이 크므로, **받기 전에 제목·화질·예상 용량을 알려주고 확인받는다**:

```bash
yt-dlp --no-download --print "%(title)s | %(duration_string)s | %(resolution)s | %(filesize_approx)s" "URL"
```

**로컬 파일** — 그대로 쓴다. 다음 단계로.

### 1-b. DVD VOB — 조각내지 말고 이어서 읽는다

`VTS_xx_1.VOB`·`VTS_xx_2.VOB` 처럼 번호가 붙은 파일은 **하나의 영상이 잘려 있는 것**이다. DVD 규격이 파일 하나를 1GB로 제한해서 생긴 분할일 뿐, 내용은 이어진다. DVD 플레이어는 이 파일들을 따로 열지 않고 **바이트를 이어 붙여 하나의 연속 스트림으로 읽는다.** 그래서 경계를 걸친 GOP도 온전히 디코딩되고 오디오도 끊기지 않는다.

**파일별로 디코딩해서 결과를 이어붙이면 반드시 실패한다.** 경계에서 정지 프레임이 생기고, 오디오 시작 타임스탬프를 손으로 맞춰야 하며, 그 보정이 또 다른 어긋남을 만든다. 실제로 그 길을 갔다가 이음매 하나 때문에 여섯 번을 다시 렌더한 적이 있다.

**올바른 절차** — 두 파일에 걸친 구간을 뽑을 때:

```bash
# 1. 앞 파일의 꼬리만 바이트째 떼어낸다 (2048 = DVD 팩 크기, 반드시 정렬)
dd if=VTS_05_2.VOB bs=2048 skip=<시작팩번호> of=tail.vob

# 2. 뒤 파일과 이어 붙인다 — 플레이어가 읽는 것과 같은 스트림이 된다
cat tail.vob VTS_05_3.VOB > seam.vob
```

떼어낼 위치는 원하는 지점보다 넉넉히 앞(1분쯤)에서 잡는다. 바이트 오프셋 = `파일크기 - 여유초 × 비트레이트/8`, 이를 2048로 내림 정렬한다.

**시각 탐색이 안 된다는 점이 중요하다.** VOB는 PTS가 깨져 있어(`ffprobe` 가 길이를 26시간으로 읽는 일이 흔하다) `-ss` 가 먹히지 않는다. 이어붙인 파일은 더 심하다. 그래서 원하는 프레임을 **찾아야** 한다:

```bash
# 기준 프레임(원본 파일에서 -ss 로 뽑은 것)과 대조해 위치를 특정
# seam.vob 앞부분을 fps 필터로 훑으며 상관계수 최대 지점을 찾는다
```

찾은 시각으로 **`trim` 필터**를 쓴다. `trim` 은 디코딩된 프레임 위에서 동작하므로 탐색이 필요 없다. `-ss` 대신 `trim=start=N` 을 쓰는 것이 핵심이다.

이렇게 하면 이어붙이는 작업 자체가 사라지므로, A/V 동기도 손댈 필요가 없다. 스트림이 원래 맞아 있다.

**분할 VOB 하나만 자를 때 (`VTS_xx_3.VOB` 단독)**

분할 파일은 타임코드가 0이 아니라 앞 파일에서 이어진 값으로 시작한다(실측 `start_time=3261`, 54분). 사용자가 말하는 「23:04」는 **그 파일 안에서의 위치**다(파일 길이 27분이라 절대 시각일 수가 없다).

🔴 **ffmpeg 는 이미 파일 시작을 0초로 맞춰 읽는다** — 영상·음성에서 같은 값을 빼주므로 둘 사이 차이(실측 0.34초)도 보존된다. 여기서 `start_time` 을 한 번 더 빼면 전부 음수가 돼 **출력이 비고**(261바이트, `No filtered frames`), 영상·음성을 `PTS-STARTPTS` 로 각각 0에 맞추면 그 0.34초가 사라져 **입이 안 맞는다.** 둘 다 같은 상수만 뺀다:

```bash
-vf "trim=start=1384:end=1604,setpts=PTS-1384/TB,bwdif=mode=1:parity=1,..."
-af "atrim=start=1384:end=1604,asetpts=PTS-1384/TB,..."
```

⚠️ 타임코드 연속성을 `ffprobe -show_entries packet=pts_time` 으로 볼 때, **B프레임은 표시 시각이 비어 있다.** 빈 값을 0으로 읽으면 가짜 「끊김」이 수만 개 나온다. 숫자인 줄만 센다.

### 1-c. 인터레이스 — 스케일 전에 반드시 푼다

DVD(NTSC)는 대부분 인터레이스다. 한 프레임을 위아래 필드로 쪼개 초당 60번 번갈아 그리는 방식이라, 그대로 확대하면 움직임마다 빗살이 생기고 **끊기는 것처럼 보인다.** DVD 플레이어는 이걸 자동으로 풀어주므로 원본은 멀쩡해 보인다 — 내 결과물만 끊긴다면 십중팔구 이것이다.

```bash
ffprobe -v error -select_streams v -show_entries stream=field_order -of default=noprint_wrappers=1 IN
ffmpeg -ss 60 -i IN -frames:v 300 -vf idet -f null - 2>&1 | grep "Multi frame"
```

`field_order=bb`(BFF) 또는 `tt`(TFF)이고 `idet` 가 BFF/TFF 를 세면 인터레이스다.

```bash
-vf "bwdif=mode=1:parity=1,hqdn3d=3:2:4:4,scale=1440:1080:flags=lanczos,setsar=1,pad=1920:1080:240:0:black,ass=cut.ass"
```

`parity` 는 `0`=TFF, `1`=BFF. `mode=1` 은 필드마다 한 장을 만들어 59.94fps 로 낸다 — 움직임이 가장 부드럽고 DVD 플레이어가 보여주는 것과 같다. **디인터레이스는 스케일보다 반드시 앞**에 온다. 순서가 바뀌면 필드가 섞인 채 확대돼 되돌릴 수 없다.

### 2. 자막 확보

위에서부터 시도한다. 위쪽일수록 품질이 좋고 시간이 덜 든다.

| 순위 | 소스 | 확인 방법 |
|------|------|-----------|
| 1 | 영상 옆의 자막 파일 (`.smi`·`.srt`·`.ass`·`.vtt`) | 같은 폴더 `ls` |
| 2 | 영상에 내장된 자막 트랙 | ffprobe 에 `codec_type=subtitle` 있는지 |
| 3 | 유튜브 공식 자막 (사람이 작성) | `yt-dlp --list-subs URL` |
| 4 | 유튜브 자동생성 자막 | 위 목록의 `auto-generated` |
| 5 | Whisper STT | 위가 전부 없을 때 |

🔴 **원어를 자막 목록으로 추측하지 마라 — 음성을 들어봐야 안다.**

`--list-subs` 에는 「Xhosa **from Spanish**」처럼 피벗 언어가 붙는데, **그건 유튜브가 자동번역에 쓴 중간 언어일 뿐 원어가 아니다.** 제목·채널명도 근거가 못 된다.

실측(Ta na manga - Inspirato): 자동번역이 전부 `from Spanish`, 제목·채널명은 포르투갈어, 스페인어 자막에는 번역자 크레딧(`Traducción por ★ ClownTube.tv ★`)까지 있었다. 그래서 원어를 스페인어로 판단했는데 — **음성 45초를 받아쓰기해보니 영어**(확신도 0.91)였다. pt·es·ko 전부 번역본이었다.

```bash
ffmpeg -ss 60 -i src.mp4 -t 45 -vn -ac 1 -ar 16000 -c:a pcm_s16le probe.wav
python3 -c "from faster_whisper import WhisperModel; \
  print(WhisperModel('small',device='cpu',compute_type='int8').transcribe('probe.wav')[1].language)"
```

**이중 자막의 아래 줄은 「들리는 언어」여야 한다.** 안 들리는 언어를 깔면 대조할 대상이 없어 쓸모가 없다. 45초 확인이 이 선택을 가른다.

**공식 자막을 쓸 때 반드시 볼 것** — 사람이 만든 자막도 트랙마다 큐를 다르게 나눈다.
- **큐 수가 다르다** (실측 한국어 54 vs 영어·스페인어 55 — 「You are an idiot. / This time you went too far.」를 한국어만 한 큐로 합침). 짝을 맞춰 병합하고, **타임코드는 한쪽을 다른 쪽에 복사**해 창을 통일한다.
- **팬자막 크레딧이 섞여 있다** (`Traducción por ★ ClownTube.tv ★`). 태우기 전에 지운다.
- **글리프 확인** — G마켓 산스에는 스페인어 악센트(`óíéúñá`)가 없어 두부가 된다. `qc.py` 의 L6 이 잡는다.

**유튜브 자막 받기:**

```bash
yt-dlp --skip-download --write-subs --write-auto-subs \
  --sub-langs "ko,ja,en" --convert-subs srt -o "subs/%(title).80s" "URL"
```

**내장 자막 뽑기:**

```bash
ffmpeg -i "INPUT" -map 0:s:0 -c:s srt out.srt
```

**SMI → SRT** (한국 자막은 대부분 SMI, 인코딩은 CP949):

```bash
python3 scripts/smi2srt.py "input.smi" "output.srt"
```

**Whisper STT** — 오디오만 뽑아서 `fw_transcribe.py` 로 돌린다:

```bash
ffmpeg -i "INPUT" -vn -ac 1 -ar 16000 -c:a pcm_s16le audio.wav
python3 scripts/fw_transcribe.py audio.wav words.json turbo ja "도메인 용어"
python3 scripts/srt_from_whisper.py words.json base.srt --max-dur 4
```

`LANG`(넷째 인자)은 알면 반드시 지정한다(자동 감지가 틀리면 통째로 엉뚱한 언어로 받아쓴다). 모델은 `turbo`(large-v3-turbo)가 기본 — medium 보다 정확하고 GPU 에서 빠르다. 5분 넘는 영상이면 백그라운드로 돌리고 위 속도표로 예상 시간을 알려준다.

**자동생성 자막·STT는 그대로 태우지 않는다.** 구두점이 없고 고유명사가 깨진다. 태우기 전에 읽고 교정한다 — 특히 사람 이름·지명·전문 용어. 교정본을 사용자에게 보여주고 넘어가는 게 안전하다.

### 2-b. 🔴 시각을 손으로 적지 않는다

**받아쓰기를 보면서 자막표를 타이핑하지 마라.** 시각을 옮겨 적다가 숫자가 틀리고, 긴 문장을 감으로 쪼개면서 경계가 밀린다. 실제로 그렇게 만든 자막에서 한 줄이 **5.4초 일찍** 떴다 — 그 사이는 대사가 아니라 동물 반응 소리였다.

더 나쁜 건 그 오류가 검사를 통과한다는 점이다. `check_sync.py --fix` 는 가장 가까운 단어로 당기므로, 근처에 무관한 단어가 있으면 거기에 고정시키고 "오차 0" 이라고 보고한다. 도구는 어느 단어가 그 자막의 것인지 모른다.

**순서를 뒤집는다 — 시각을 먼저 확정하고, 번역은 그 위에 글자만 얹는다.**

```bash
# 1. 시각이 박힌 원어 껍데기를 만든다
python3 scripts/srt_from_whisper.py words.json base.srt --max-dur 8

# 2. base.srt 의 각 큐에서 '텍스트 줄만' 번역으로 바꾼다.
#    번호와 타임코드 줄은 절대 건드리지 않는다.
```

이렇게 하면 시각에 손댈 여지가 없으므로 어긋날 수가 없다. 실제로 이 방식으로 만든 자막은 자동 교정 없이 **중앙 오차 0.000초**로 통과했다.

`--max-dur` 는 긴 큐를 고르게 나눈다. 받아쓰기는 여러 문장을 한 덩어리로 뭉쳐 놓기도 하는데(41초짜리를 만난 적 있다), 그대로 두면 번역에서 문장이 통째로 빠진다.

번역할 때 **큐를 합치거나 나누고 싶어지면 참아라.** 그 순간 시각을 손으로 만지게 된다. 한 큐가 어색하면 그 큐 안에서 문장을 다듬는다.

**한 큐에 한 문장.** `--max-dur 8` 은 읽기엔 길다 — 한 큐가 원어 두세 문장을 담으면 번역도 두세 문장이 되고, 화면엔 마침표가 여러 개 찍힌 벽이 뜬다. 뒷 문장이 잘려 마침표 없이 끝나기도 한다. **번역을 얹기 전에 `--max-dur 4` 로 다시 뽑아** 큐 하나가 문장 하나가 되게 만든다. 그다음 각 큐에 한 문장씩, 종결부호를 일관되게 붙여 쓴다.

`split_long()` 은 끊을 자리를 고를 때 **쉼표·마침표 뒤를 최우선**으로 본다(없으면 가장 벌어진 곳). 이게 없으면 `While his back was turned, this` / `kid did what...` 처럼 구절 한가운데서 잘린다 — 4초로 조였을 때 66개 중 61개가 그렇게 잘렸고, 구두점 우선을 넣은 뒤 5개로 줄었다.

### 2-c. 🔴 렌더 전에 자막표를 대화창에 올린다

번역을 얹었으면 **태우기 전에** 큐 번호·시각·원문·번역을 표로 대화창에 출력한다. 유저가 쭉 읽으며 어색한 번역을 잡는다.

- **툴 출력은 유저에게 안 보인다.** `python3 ... | print` 결과는 나만 본다. 반드시 **응답 본문에 마크다운 표로 직접 적는다.**
- 원문(EN)을 **같이** 보여준다. 번역만 보면 판단이 안 된다.
- 받아쓰기가 틀린 자리를 미리 짚어준다(예: `seized the Professor` → 실제 `sees`). 유저가 원문을 못 믿을 근거를 알아야 한다.
- 수정 요청이 오면 **그 줄만** 바꾸고 타임코드는 안 건드린다.
- 큐 **병합**은 허용된다 — 앞 큐 시작 + 뒤 큐 끝은 둘 다 측정값이라 싱크가 안 깨진다. 병합 후 `align_second_lang.py` 를 다시 돌려 두 번째 언어의 큐 수를 맞춘다. (분할은 안 된다 — 없던 경계를 손으로 찍게 된다.)

렌더는 3분 걸린다. 자막을 먼저 보여주면 한 번에 끝난다.

🔴 **수정 한 건마다 재렌더하지 않는다.** 유저가 자막 전체를 훑는 중이면 지적은 여러 번에 나눠 온다. 그때마다 태우면 3분짜리 렌더를 대여섯 번 돌리게 된다. **SRT만 고쳐두고, "이제 렌더해줘"에 해당하는 신호가 올 때까지 기다린다.** 수정 반영은 대화창에 그 줄만 보여주면 된다.

### 3. 구간 자르기

영상과 자막을 **같은 기준으로** 자른다. 자막만 안 자르거나 시프트를 빼먹으면 통째로 어긋난다.

```bash
python3 scripts/srtcut.py full.srt cut.srt 19:20 31:50
```

`srtcut.py`는 구간의 큐만 남기고 시작 시각을 0으로 당긴다. 경계에 걸친 큐는 잘라서 살린다.

영상 자르기는 4단계 인코딩에 `-ss`/`-t`로 합쳐서 한 번에 한다(따로 자르면 재인코딩이 두 번 된다).

### 3-b. 자막 유지 시간 늘리기

받아쓰기가 만든 자막은 말이 끝나는 순간 사라진다. 읽는 사람은 문장을 다 읽기도 전에 글자를 뺏기고, 대사가 짧게 이어지는 구간에서는 자막이 깜빡이는 것처럼 보인다. 그렇다고 무조건 늘리면 아무도 말하지 않는 긴 구간에 옛 자막이 남아 화면을 덮는다.

```bash
python3 scripts/hold_subs.py cut.srt cut.hold.srt --gap 5 --tail 3
```

- 다음 자막까지의 공백이 **5초 이하**면 다음 자막 직전까지 유지한다
- 공백이 **5초를 넘으면** 말이 끝나고 3초만 더 두고 사라진다
- 앞 자막의 끝과 뒤 자막의 시작을 **딱 붙인다**. 사이에 조금이라도 틈을 두면 그 순간 자막이 사라져 깜빡이는 것처럼 보인다

값은 소재에 따라 조절한다. 대사가 촘촘한 토크 영상은 기본값이 무난하고, 연주·공연처럼 말 사이가 긴 영상은 `--gap` 을 줄여 빈 화면을 살린다.

### 4. 자막 스타일 만들기

`force_style` 을 명령줄에 욱여넣는 대신 ASS 파일을 만든다. 따옴표·쉼표 이스케이프 지옥을 피하고, 결과를 눈으로 확인·수정할 수 있다.

```bash
# 단일 자막
python3 scripts/make_ass.py --srt cut.srt --out cut.ass --width 640 --height 480

# 이중 자막 (원어 위 + 번역 아래) — 기본 선택
python3 scripts/make_ass.py --srt cut.ja.srt --srt2 cut.ko.srt --out cut.ass \
  --width 1920 --height 1080 --preset dual
```

폰트는 자동으로 잡히지만 명시할 수 있다: `--font "Apple SD Gothic Neo"`, `--font2 "Hiragino Sans"`. 크기·색·위치는 `--size`·`--size2`·`--color2`·`--margin`.

프리셋:
- `single` — 흰색 볼드 + 검정 외곽선. 한 언어일 때.
- `dual` — 원어 위(흰색, 크게) + 번역 아래(옅은 회색, 조금 작게).
- `hikaro` — 원어 흰색 + 번역 에메랄드(`#00E7A7`) 볼드. 히카로 영상 확정 스타일.

### 4-b. 출력 해상도 — 기본 1080p

**최종본은 1920×1080 으로 뽑는다.** 원본이 640×360 이어도 마찬가지다.

업스케일이 없던 디테일을 만들어내지는 않는다. 그런데도 1080p 로 내보내는 이유는 유튜브 때문이다. 유튜브는 **해상도 티어별로 비트레이트를 다르게 배정**하고 1080p 이상에만 VP9/AV1 을 붙인다. 720p 로 올리면 배정이 짜서 재인코딩 손상이 눈에 띄게 커진다. 같은 소스라도 1080p 로 올린 쪽이 확실히 깨끗하다.

자막도 출력 해상도로 새로 그려지므로, 1080p 로 뽑으면 저해상도 원본에서도 글자만은 선명하다. 640×360 native 로 태우면 자막이 12px 로 뭉개진다.

옛날 방송 녹화본은 **노이즈 제거를 먼저** 건다. 아날로그 그레인이 화면에 깔려 있으면 유튜브 인코더가 그걸 디테일로 착각해 비트레이트를 거기 쓴다. 미리 지우면 그 예산이 실제 움직임으로 간다.

```bash
-vf "hqdn3d=3:2:4:4,scale=1920:1080:flags=lanczos,ass=cut.ass"
```

필터 순서가 중요하다 — 노이즈 제거는 **작은 원본 상태에서** 해야 빠르고 효과적이고, 자막은 **업스케일 뒤에** 그려야 선명하다.

샤픈(`unsharp`)은 넣지 않는다. 저해상도 업스케일에 걸면 윤곽에 헤일로가 생기고, 그 헤일로를 인코더가 또 비트레이트로 떠안는다.

해상도별 자막 크기 기준값 (`--size`, 세로 보정은 크기마다 다시 재야 한다):

| 출력 | `--size` | `--box-nudge-y` |
|------|----------|-----------------|
| 1920×1080 | 36 | +1 |
| 1280×720 | 24 | +1 |
| 640×360 | 12 | 0 |

### 5. 태우기

> 🔴 **태우기 전에 `scripts/qc.py` 를 돌려 FAIL 0 을 확인한다** (6-g). 렌더는 몇 시간이 들고 되돌릴 수 없다.

```bash
bash scripts/burn.sh "INPUT" cut.ass "OUTPUT.mp4" --ss 19:20 --t 12:30
```

내부적으로 `ffmpeg@7`을 쓰고, 필터 존재를 먼저 확인하고, 없으면 설치 명령을 알려준다. 직접 쓰려면:

```bash
/opt/homebrew/opt/ffmpeg@7/bin/ffmpeg -ss 1160 -i "INPUT" -t 750 \
  -vf ass=cut.ass -c:v libx264 -crf 18 -preset medium -pix_fmt yuv420p \
  -af "loudnorm=I=-16:TP=-1.5:LRA=11" -ac 2 -ar 48000 -c:a aac -b:a 192k \
  -movflags +faststart -y "OUTPUT.mp4"
```

오디오 쪽 `-ac 2` 는 5.1 소스가 섞여 들어와도 대사가 살아남게 하는 안전망이고, `loudnorm` 은 옛날 방송 녹화본처럼 평균 음량이 -30dB 대로 낮은 소스를 웹 기준(-16 LUFS)으로 올린다. 둘 다 걸어두면 "소리가 안 들린다"는 재작업이 사라진다.

`-ss`를 `-i` 앞에 두면 빠르게 탐색하면서도 프레임 정확하고, 출력 타임스탬프가 0부터 시작한다. 그래서 3단계에서 자막을 0 기준으로 시프트해 둔 것이다.

### 5-b. 🔴 태우기 전에 — 소프트섭이면 끝나는 일인지 먼저 묻는다

**하드섭(태우기)은 되돌릴 수 없고 비싸다.** 1시간 48분짜리를 태우면 2~3시간에 4GB가 나온다. 같은 결과를 **25초에 826MB**(원본 그대로)로 낼 수 있는 길이 있다 — 자막을 트랙으로 심는 것이다.

```bash
# 이중 자막을 트랙 하나로 (같은 타임코드의 두 SRT를 두 줄로 합친다)
python3 scripts/merge_dual_srt.py ko.srt en.srt dual.srt
python3 scripts/hold_subs.py dual.srt dual.hold.srt --gap 5 --tail 3

# 영상 재인코딩 없이 자막 트랙만 심는다 (-c copy)
ffmpeg -i IN.mp4 -i dual.hold.srt -i ko.srt -i en.srt -map 0 -map 1 -map 2 -map 3 \
  -c copy -c:s mov_text \
  -metadata:s:s:0 language=kor -metadata:s:s:0 title="KR+EN" \
  -metadata:s:s:1 language=kor -metadata:s:s:1 title="한국어" \
  -metadata:s:s:2 language=eng -metadata:s:s:2 title="English" \
  -movflags +faststart "OUT [sub].mp4"
```

**하드섭이 필요한 경우는 셋뿐이다.** 그 외에는 소프트섭이 낫다.
1. 유튜브 등에 **올릴 때** — 플랫폼이 스타일을 무시하고, 업로더가 자막을 따로 올려야 한다
2. **스타일을 살려야 할 때** — G마켓 산스·자막바·영어 절반 크기는 태워야만 그대로 나온다. 소프트섭은 플레이어 기본 스타일이다
3. 자막을 지원하지 않는 기기

**파일명이 곧 자동 로드 규칙이다.** `영상.mp4` 옆에 `영상.srt`·`영상.ko.srt` 를 두면 VLC·IINA·infuse 가 알아서 불러온다. 묶지 않아도 되는 경우가 많다.

### 6. 검수 — 타이밍은 수치로, 렌더는 눈으로

**두 가지를 나눠서 본다.** 프레임을 보는 것으로는 타이밍을 못 잡는다. 87개 자막 중 서너 개만, 그것도 "떠 있다" 수준으로 보게 되기 때문이다. 실제로 프레임 검수를 통과한 결과물에서 14개가 어긋나 있었고, 그걸 사용자가 먼저 발견한 적이 있다.

#### 6-a. 타이밍 — 전 자막을 수치로 (건너뛰지 않는다)

결과물의 오디오를 **다시 받아쓰기해서** 자막 시각과 대조한다. 만들 때 쓴 받아쓰기를 재활용하지 않는 이유는, 그 사이에 손으로 옮겨 적은 시각·문장 쪼개기 같은 사람 실수가 끼어들기 때문이다. 실제로 그 단계에서 오차가 생겼다.

```bash
ffmpeg -i OUT.mp4 -vn -ac 1 -ar 16000 -c:a pcm_s16le out.wav
python3 scripts/fw_transcribe.py out.wav out.json turbo en

python3 scripts/check_sync.py cut.hold.srt out.json --tol 0.3
```

`--tol 0.3` 이 기본. 초과분이 있으면 목록으로 나오고 종료 코드가 1이다.

🔴 **`check_sync.py` 는 「전체가 일정하게 밀린 것」을 못 잡는다.** 자막마다 *가장 가까운 단어*를 찾아 오차를 재는 방식이라, 말이 촘촘한 소재(단어 2,586개짜리 12분 영상)에서는 **어떤 오프셋에서도 0.5초 안에 단어가 하나쯤 있다.** 실제로 **0.53초 밀린 자막이 「중앙 오차 0.065초」로 통과**했고, 사용자가 보고 나서야 발견됐다.

**그래서 오프셋 스윕을 따로 돌린다.** 기준을 단어가 아니라 **발화 시작점**(앞 단어와 0.4초 이상 떨어진 단어 = 새로 말을 시작하는 순간)으로 바꾸고, -3~+3초를 훑어 일치 개수가 가장 많은 지점을 찾는다.

```bash
python3 scripts/find_offset.py cut.srt words.json              # 진단만
python3 scripts/find_offset.py cut.srt words.json --apply fixed.srt   # 최적 오프셋 + 스냅 적용
```

봉우리 모양으로 판정한다 — **뾰족하면 진짜 밀림**(실측: 0초에서 50/174 → -0.53초에서 98/174), **평평하면 이미 맞은 것**(보정 후: 99~108로 평탄). 구간별 오프셋도 같이 찍히는데, 값이 한 방향으로 흐르면 프레임레이트 불일치를 의심한다.

⚠️ **두 번째 언어 자막에도 같은 보정을 그대로 적용**해야 이중 자막의 짝이 유지된다.

⚠️ **`--fix` 는 최후 수단이다.** 가장 가까운 단어로 당길 뿐 어느 단어가 그 자막의 것인지는 모른다. 근처에 무관한 단어가 있으면 엉뚱한 자리에 고정시키고도 "오차 0" 으로 보고한다 — 실제로 그렇게 5.4초 어긋난 자막이 검사를 통과했다. 초과분이 나오면 `--fix` 로 덮지 말고 **2-b 절대로 껍데기부터 다시 만드는 쪽**이 옳다.

받아쓰기가 놓친 말(웃음에 묻힌 대사 등)은 기준점이 없어 오검출될 수 있으니 목록은 눈으로 한 번 훑는다. 자동 수정은 tol 안에 기준점이 있는 것만 건드린다.

#### 6-b. 렌더 — 프레임을 눈으로

```bash
/opt/homebrew/opt/ffmpeg@7/bin/ffmpeg -ss 95 -i "OUTPUT.mp4" -frames:v 1 -y check1.png
```

**자막이 실제로 있는 시각**을 골라 2장 이상 뽑고 Read 도구로 직접 본다. 여기서 잡는 것은 글자 깨짐(두부), 화면 밖 잘림, 자막바 크기 — **렌더링 사고**다. 타이밍은 6-a 가 담당한다.

#### 6-c. 번역 — 원문 대조

받아쓰기 원문과 자막을 나란히 놓고 빠진 문장이 없는지 본다. 특히 **한 큐가 10초를 넘는 구간**은 받아쓰기가 여러 문장을 뭉친 자리라 번역에서 통째로 빠지기 쉽다. 실제로 8초짜리 대목이 자막에서 사라진 적이 있다.

사용자에게 "됐다"고 말하기 전에 세 가지가 모두 통과해야 한다.


### 6-g. 🔴 검수는 층으로 나눈다 — `qc.py`

**한 가지 검사로는 못 잡는다.** 이 스킬에서 터진 사고를 모아보면 전부 다른 층에서 났고, **아래 층이 통과했다고 위층이 보장되지 않는다.** 싱크가 완벽한데 이중자막이 단어 중간에서 잘려 있었고, 번역이 완벽한데 폰트에 글리프가 없어 두부가 떴다.

| 층 | 무엇을 본다 | 실제로 터진 사고 | 누가 |
|----|------------|----------------|------|
| **L0** 소스 | 컨테이너·인터레이스·PTS·오디오 채널 | `.avi`가 실은 Matroska / VOB PTS 26시간 / 5.1이라 대사 실종 | 0·1-b·1-c 절 |
| **L1** 큐 구조 | 큐 수, 두 트랙 타임코드 동일, 겹침, 빈 큐 | 두 줄을 한 줄로 써서 **116큐 밀림** | `qc.py` |
| **L2** 시각 | 전체 밀림(오프셋 스윕), 드리프트 | **0.53초 밀림**이 check_sync 를 통과 | `qc.py`·`find_offset.py` |
| **L3** 원문 | STT 의 도메인 용어·고유명사 | `call`→cull 172곳 / `記述`→奇術 | 6-e 절 |
| **L4** 번역 | 뜻·한 큐 한 문장·용어 통일 | 멸치볶음(메르시 보쿠) / 기술부(마술부) | 사람 (2-c 표) |
| **L5** 짝 맞춤 | 각 줄이 그 자체로 읽히는가 | **栃木生ま / れの** 단어 중간 절단 | `qc.py` + 눈 |
| **L6** 렌더 전 | 폰트 글리프 커버리지, 줄 폭 | G마켓 산스에 일본어 없음 → 두부 193종 | `qc.py` |
| **L7** 전달 | 소프트/하드 판단, 파일명, 폴더 | 2~3시간 렌더가 25초로 끝날 일이었음 | 5-b 절 |

```bash
python3 scripts/qc.py --kr ko.srt --other ja.srt --words seg.json \
  --font "Gmarket Sans Medium" --size 36 --font2 "Hiragino Sans" --size2 18 --width 1920
```

**태우기 전에 FAIL 0 을 확인한다.** 렌더는 되돌릴 수 없고 몇 시간이 든다. L6 는 특히 렌더 전에만 의미가 있다 — 두부는 태우고 나면 다시 태우는 수밖에 없다.

**판정 기준 (실측으로 정한 값)**
- L2 전체 밀림: 봉우리 **비율**로 본다. 진짜 밀림은 `50→91 (1.82배)`, 보정 후 잔여는 `99→108 (1.09배)`. **1.30배 이상 FAIL**, 1.12~1.30 warn. 절대 증가분으로 보면 잘 맞는 자막도 걸린다.
- L2 드리프트: 폭 0.6초 초과 **+ 한 방향으로 단조 증가/감소**일 때만 FAIL. 구간별 측정은 원래 ±0.1초쯤 흔들린다.
**L3 환각 — 웃음·박수 위에 지어낸 대사**

실측(Slydini): 인터뷰어가 크게 웃은 3초를 받아쓰기가 앞 문장의 세기 패턴에 이어 「number three, number four, number five」로 만들었다. 「이번엔 두 개뿐」이라고 말한 직후라 내용상으로도 불가능했고, **사용자가 먼저 발견했다.**

흔적 → 판정 2단계:
1. **의심**: 단어 시각이 이상하다 — 길이 0인 단어(`number` 20.30~20.30), 비정상적으로 늘어진 단어(`four` 1.28초). 구간이 영상에서 가장 시끄럽다(RMS 5034, 평소 1200~3400).
2. **확정**: 그 구간만 단독 재받아쓰기(`--wav seg.wav`). ⚠️ **「뭔가 받아써지면 진짜 말」은 틀린 기준** — VAD 가 웃음을 통과시키고 모델이 또 다른 환각(`You can't do that.` ×2)을 만든다. 구분선은 **무음확률 ≥0.4 AND 확신도 ≤-0.9**, 또는 같은 문장 반복. 진짜 말은 무음확률 0.12~0.32였다(억양 심해 이탈리아어로 오인된 구간도 0.12로 통과).

```bash
python3 scripts/qc.py --kr ko.srt --other en.srt --words seg.json --wav seg.wav
```

⚠️ **cpp 엔진(whisper.cpp) 받아쓰기면 L3 「0초 단어」 경보가 수백 개 뜬다** — 토큰 시각이 거칠어서 생기는 가짜다(실측 Woody DVD1: 2,783큐 중 약 450개, 싱크 L2 는 정상). 이때 L3 은 무시하고, 대신 **긴 세그먼트(20초+)·영상 끝 음악 구간**을 눈으로 본다. 실측으로 끝 크레딧 음악 위에 `To be continued...`·`Thank you.`·`Transcription by CastingWords` 3줄이 지어져 있었다.

FAIL 이 뜨면 그 큐를 **양쪽 트랙에서 같이 지운다.** `fw_transcribe.py` 는 이제 단어 확신도·세그먼트 무음확률을 저장한다.

**L3x 두 번째 받아쓰기 대조 — 단어 하나만 틀린 오류**

문장 전체는 맞고 **단어 하나만** 틀리면 어떤 검사에도 안 걸린다. 실측(Slydini): `no skews`(→excuse), `brilliant is not so good`(→believe me), `I came over here`(→I can put here). 유튜브에 자동자막(`en-orig`, 구글 음성인식)이 있으면 **독립된 두 번째 의견**으로 쓴다:

```bash
yt-dlp --skip-download --write-auto-subs --sub-langs "en-orig" --convert-subs srt -o yt URL
python3 scripts/qc.py ... --ref yt.en-orig.srt
```

한쪽만 들은 내용어를 큐별로 뽑는다. **구글도 틀린다**(`robber bent`=rubber band) — warn 이고 사람이 고른다. 셋째 의견이 필요하면 그 구간만 `large-v3` 로 다시 받아쓴다(1번은 3개 모델이 전부 `no excuse`).

⚠️ **받아쓰기가 뜻이 안 되는 단어를 냈을 때 문맥으로 추측해서 채우지 마라.** 1번 `no skews` 를 17번의 소매 얘기에 끌려 `no sleeves` 로 채웠는데 틀렸고, 사용자가 잡았다. 추측 대신 두 번째 받아쓰기로 확인한다.

**L5 의 진짜 판별식 — 「일본어가 조사로 끝나는가」가 아니라 「한국어도 같은 자리에서 끊기는가」**

두 트랙은 어순이 달라서 일본어가 조사로 끝나는 일 자체는 흔하고, 대부분 정상이다. 한국어도 같이 끊기면 짝이 맞아 읽는 데 문제가 없다.

```
정상 (짝 맞음)          #65  KR …스페이드 에이스는   JP …スペードのエースは
깨짐 (짝 어긋남)        #15  KR 일본의 고무줄 마술.  JP 日本の…
```

**한국어는 문장을 끝냈는데(다./요./?) 일본어만 조사로 매달려 있으면** 그게 기계가 시간으로 잘라 만든 가짜 경계다. 이 규칙 하나로 실측 7곳 중 5곳을 정상으로 걸러내고 2곳만 남겼다.

⚠️ **말줄임표로 덮지 마라.** 절단을 발견하고 「日本の…」처럼 `…` 를 붙였더니, 「부호로 끝나면 정상」 규칙에 걸려 **경보만 꺼지고 절단은 그대로 남았다.** `qc.py` 는 이제 `…`·`、` 를 벗겨내고 판정한다.

- L5 어절 절단: warn 으로만 낸다. 「国 / で、」처럼 조사 경계면 괜찮고 「生ま / れの」면 고쳐야 하는데, 기계가 구별 못 한다. 눈으로 본다.

**warn 은 무시해도 되는 게 아니라 "사람이 보라"는 뜻이다.**

### 6-d. 긴 영상(30분 이상) — 절차가 달라진다

2-c 의 「대화창 표 검수」는 큐가 수백 개를 넘으면 성립하지 않는다. 1시간 48분짜리에서 **2,255큐**가 나왔다. 표로 올리면 수십 페이지다.

**대신 SRT 파일을 산출물로 준다.** 사용자가 직접 열어 훑고, 고칠 곳을 알려주면 그 줄만 고친다.

**받아쓰기는 `fw_transcribe.py` 로** (GPU 엔진 자동 선택).

```bash
python3 scripts/fw_transcribe.py seg.wav seg.json turbo en "도메인 용어를 여기 나열"
```

⚠️ **속도를 부풀려 말하지 마라.** faster-whisper CPU 를 「4~8배」로 예고했다가 실측 **1.5배**가 나왔다. 예고는 위 속도표의 실측값으로, 그리고 `--check` 로 확인한 엔진 기준으로 한다. 맥 GPU(whisper.cpp)로 바꾼 뒤 2시간 30분 DVD 가 몇 분대로 줄었다(2026-11-20).

**두 컴퓨터로 나눠 돌리기** — 시리즈(DVD 여러 장)는 맥·윈도우가 한 장씩 맡아도 된다. 받아쓰기에 필요한 건 소리뿐이라 `audio.wav`(16kHz 모노, 2.5시간 ≈ 290MB) 또는 `ffmpeg -i IN -vn -ac 1 -ar 16000 -c:a flac a.flac`(더 작음)만 옮기고, 결과 `words.json`(몇 MB)만 돌려받는다.

**번역은 배치로, 큐 수를 매번 검증한다.**

```bash
python3 scripts/patch_srt.py 201 <<'EOF'   # ko.srt 는 en.srt 복사본으로 시작
(200줄)
EOF
# -> "201~400 반영 (200큐)" 가 찍힌다. 199 가 찍히면 한 줄을 빠뜨린 것이다.
```

🔴 **한 줄이라도 어긋나면 그 뒤가 전부 밀린다.** 실제로 283·284 번을 한 문장으로 합쳐 써서 **116큐가 밀렸다.** 출력의 큐 수가 예상과 다르면 그 자리에서 멈추고 원인을 찾는다 — 계속 진행하면 밀린 채로 굳는다.

### 6-e. 도메인 용어는 두 번 잡는다

받아쓰기는 그 분야 용어를 **일관되게** 틀린다. 한 번 틀리면 끝까지 틀린다.

**① 사전 주입** — `--initial_prompt` 에 그 영상의 용어를 나열한다.
**② 사후 일괄 교정** — 그래도 놓친 건 전수 치환한다. 실제 사례:

| 받아쓰기 | 실제 | 건수 |
|---|---|---|
| `call` | `cull`(컬 기법) | 172 |
| `the risks` | `the wrists`(손목) | 2 |
| `injured`·`injury` | `in-jog`(인조그) | 3 |
| `Kosher Kilm` | `Kostya Kimlat` | 1 |
| `king of Spain` | `king of spades` | 1 |

🔴 **일괄 치환에는 반드시 예외 목록을 만든다.** `call→cull` 172곳을 바꿨더니 **진짜 `call` 5곳이 망가졌다** — `The Queen of Hearts **calls** its friends`(하트 퀸이 친구들을 **부른다**)는 이 공연의 반복 개그이고, `something I like to **call** "And If All Goes Wrong"` 은 마술 제목이다. 치환 전에 문맥을 grep 으로 훑어 「이름 붙이는 call」을 골라낸다:

```bash
grep -inE "\b(I|we|they|you|it'?s)\s+call(ed|s)?\s+(it|this|that|the|a)\b|so-?called|what I call" en.srt
```

**영어 자막도 같이 고친다.** 이중 자막에서 아래 줄이 `gets injured`(다쳤다)로 뜨면 한국어가 맞아도 결과물이 틀린 것이다.

### 6-f. 오래 도는 명령은 파이프로 감싸지 마라

`ffmpeg ... | tail -2`, `whisper ... | tail -40` 처럼 쓰면 **파이프가 출력을 전부 버퍼링해서 끝날 때까지 한 글자도 안 나온다.** 진행률을 볼 수 없고, 사용자가 「어디까지 됐어?」라고 물어도 답할 수가 없다. 이 세션에서 두 번 반복한 실수다.

진행률이 필요하면 파이프 없이 그대로 돌리고, 로그가 길면 파일로 리다이렉트한 뒤 `tail -f` 로 본다.


## 이중 자막 규칙

기본은 이중 자막이다. 다만 다음은 예외로 두고 사용자에게 확인한다:

- **원어가 한국어면** 번역이 무의미 → 단일
- **자막을 유튜브에 올릴 목적**이면 이중은 화면을 많이 먹는다 → 물어본다
- **화면에 이미 자막·자료 화면이 많으면** (예능·정보 프로그램) 두 줄이 겹친다 → 단일 권장

번역은 원본 SRT의 타임코드를 그대로 유지한 채 텍스트만 바꿔 만든다. 큐 번호와 개수를 보존해야 `make_ass.py`가 짝을 맞출 수 있다. 큐를 합치거나 나누고 싶어지면 참고 → `references/troubleshooting.md`.

## 산출물

작업 폴더에 남긴다. 이름은 구간이 드러나게:

```
<원본이름>_19m20s-31m50s_sub.mp4    ← 자막 태운 최종본
<원본이름>_19m20s-31m50s.mp4        ← 자막 없는 구간 (편집용)
<원본이름>.ko.srt                    ← 전체 자막
```

자막 없는 버전도 같이 주면 좋다 — 파이널컷 등에서 다시 편집할 여지가 남는다. 중간 파일(`cut.srt`·`cut.ass`)은 스크래치패드에 두되, 사용자가 스타일을 고치고 싶어할 수 있으니 경로는 알려준다.

**마지막에 결과 폴더를 연다** — 어차피 결과물을 눈으로 확인해야 하고, 파일이 여러 개면 어느 게 최종본인지 비교하게 된다. 경로만 알려주고 끝내지 않는다.

```bash
open "/path/to/output/folder"
```

## 파이널컷으로 넘길 때

FCP는 mkv·Vorbis·AVI를 못 읽는다. 자막 태우지 말고 이렇게 넘긴다:

1. 구간을 H.264+AAC MP4(또는 ProRes MOV)로 변환 — 기본 `ffmpeg`으로 충분
2. FCP에서 **파일 > 가져오기 > 자막**으로 `cut.srt` 임포트
3. SRT가 0초 기준이면 "재생헤드 위치에 삽입", 프로젝트 타임코드 기준이면 "절대 타임코드"

FCP 캡션은 스타일 자유도가 낮다. 색·폰트를 살려야 하면 이 스킬로 태우는 쪽이 낫다.
